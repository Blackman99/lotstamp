    Plate 1 · what the light shows

    The fix left a fingerprint in every binary

    The CVE-2026-111497 fix (Brotli 1.2.1, backported as 1.1.1 and 1.0.10) adds one new error code, BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH (-17). The decoder keeps a table of its error names as strings, so the fix is visible in the compiled code: a pre-fix decoder has 16 FORMAT_ names, a fixed one has 17.

    lotstamp streams each file once, finds that table and checks for the 17th name. Nothing is run, so a 300 MB Electron binary takes about a second, and a hostile binary gets no chance to act.

    Plate 2 · the stamp lies one way

    Every Bun binary says “Node 26.3.0”

    Bun embeds the URL nodejs.org/download/release/v26.3.0/node-v26.3.0-headers.tar.gz, its Node-compat level. A check that greps for the Node version calls Claude Code 2.1.310 and OpenCode 1.19.4 vulnerable, because 26.3.0 is older than 26.12.1.

    Neither runs Node. Both run Bun 1.4.4, which shipped the fix on 22 Oct. lotstamp reads the Bun version too, and reports the stamp only as a note: version contains a Node 26.3.0 headers URL · but that is Bun's Node-compat level.

    Plate 3 · and the other way

    Cursor embeds Node 24.19.0, and is fixed anyway

    Electron builds Node against Chromium's copy of Brotli, not Node's (deps/brotli is swapped for //third_party/brotli:dec in Electron's GN patch). Chromium took the upstream fix in M148, months before the CVE was published.

    So Cursor 3.27.12, Windsurf 1.126.0, VS Code 1.143.1 and Kiro 1.4.26 all embed a Node older than 24.22.1, and all four carry the 17th name. Reading the stamp, you would file four tickets. Reading the decoder, none.

    Plate 4 · the egg behind the egg

    Debian's node doesn't carry a decoder at all

    Debian builds Node with --shared-brotli. /usr/bin/node is 26 KB; the code lives in libnode.so.115, which links libbrotlidec.so.1. Upgrading Node does nothing here. The fix is libbrotli1 1.1.0-2+deb13u1 (DSA-6582-1).

    Naive string scanners trip here too: libnode holds the 16 pre-fix names as zlib.constants strings, frozen from the headers at build time. Grade libnode and it stays BEHIND after you install the fixed libbrotli1. lotstamp sees the dynamic link, grades the library that actually decodes, and prints used by /usr/bin/node (Node 20.19.2) via libnode.so.115 → libbrotlidec.so.1.

    Plate 5 · the one nobody stamps

    A pre-fix decoder inside VS Code that isn't Node

    VS Code 1.143.1 ships @vscode/vsce-sign, a .NET NativeAOT program used to verify extension signatures. It has Brotli compiled in, and it is pre-fix: 16 names, no BLOCK_SWITCH. Whether untrusted Brotli data can ever reach it depends on the program, so lotstamp says so and marks it who: vendor.

    No version check finds this one. There is no Node version to read.

    The grading chart

    Each decoder gets one grade, a fix command and who has to act: you, the vendor or your distro.

    • FIXEDBLOCK_SWITCH is in the decoder, or the distro package is at its fixed version.exit 0
    • BEHINDPre-fix decoder code. The fix line names the release that has it.exit 3
    • NO-FIX-LINEPre-fix, on a Node line that gets no release (20, 21, 23, 25). Move lines.exit 3
    • UNKNOWNLight can't get in: an AppImage or packed payload. Extract it and scan again.exit 0, or 3 with --fail-on unknown
