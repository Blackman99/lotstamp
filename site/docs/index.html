The grading manual

lotstamp opens every file that can carry a Brotli decoder (Node, Bun, Electron apps, Python modules, system libraries), looks for the error name the CVE-2026-111497 fix added, and grades each copy. It reads bytes. It never starts a binary, so a backdoored or broken one can't do anything while it is checked.

1Install

One static Go binary for Linux, macOS and Windows (amd64, arm64). The script picks the right archive from the latest release, checks it against checksums.txt, and puts it in ~/.local/bin.

curl -fsSL https://blackman99.github.io/lotstamp/install.sh | sh

It is 51 lines; read it first if you'd rather. Other ways:

# Go 1.22+
go install github.com/Blackman99/lotstamp/cmd/lotstamp@latest

# by hand: pick an archive, check it, unpack
https://github.com/Blackman99/lotstamp/releases/latest

LOTSTAMP_BIN=/usr/local/bin changes where the script installs; LOTSTAMP_VERSION=v0.1.0 pins a release.

2Usage

With no arguments it reads this machine: everything on PATH (following npm, pnpm and bun launcher scripts to the binary they start), nvm, volta, fnm, mise, asdf and n installs, ~/.bun, native AI coding tool installs (Claude Code, OpenCode, Cursor agent, Windsurf), the binaries inside global npm/pnpm/bun packages (Codex, Claude Code and OpenCode ship them there), Electron app bundles in /Applications, /opt, /usr/share, Program Files and AppData\Local\Programs, AppImages, Python Brotli modules in site-packages, and the commands your MCP configs launch.

lotstamp                       # this machine
lotstamp dist/ build/app.AppImage   # only these files or folders
lotstamp --all                 # also list files with no decoder
lotstamp --json > report.json  # for scripts
lotstamp advisory              # what is checked, and the sources

A finding reads like this (a Debian 13 box before apt upgrade):

BEHIND      Brotli decoder library libbrotlidec.so.1.1.0  /usr/lib/x86_64-linux-gnu/libbrotlidec.so.1.1.0
            system libbrotli1 1.1.0-2+b7
            decoder  pre-fix code: 16 decoder error names, no BLOCK_SWITCH
            used by  /usr/bin/node (Node 20.19.2)  via libnode.so.115 → libbrotlidec.so.1
                fix  sudo apt update && sudo apt install --only-upgrade libbrotli1
                     (fixed in 1.1.0-2+deb13u1, DSA-6582-1)  · who: you

who says who can fix it: you (upgrade it yourself), vendor (the runtime is bundled inside someone's app; update the app or wait for them), or distro (a shared library that comes with your OS packages).

3GitHub Action

Fail a build when something you ship still carries the old decoder: an Electron app, a Bun-compiled CLI, a container rootfs, a vendored Node.

- uses: Blackman99/lotstamp@v0
  with:
    paths: dist/ out/linux-unpacked/   # empty = the runner itself
    fail-on: behind                    # behind | unknown | never
inputdefaultmeaning
pathsemptyFiles or folders to read, space-separated. Empty reads the runner like lotstamp with no arguments.
fail-onbehindunknown also fails on packed AppImages it can't open; never only reports.
versionlatestRelease tag of lotstamp to download (checksum checked).

The text report goes to the job log and the step summary; output report is the path of the JSON report, for an upload-artifact step.

There is no config file. The advisory data (fix marker, fixed versions, distro backports) is compiled in; lotstamp advisory prints it with its sources.

5Grades & exit codes

FIXED
The decoder's error-name table contains BLOCK_SWITCH, the name the fix added. Whatever the version string says.
BEHIND
The table is there (at least 12 of the 16 older names) and BLOCK_SWITCH isn't. Exit 3.
NO-FIX-LINE
Behind, and the runtime's release line gets no fix (Node lines other than 22, 24 and 26). Upgrading within the line won't help. Exit 3.
UNKNOWN
There is a decoder but no readable answer: a compressed AppImage payload, or a Brotli library without an error table. Files it may not open are listed as skipped instead. Exit 3 only with --fail-on unknown.
NO-DECODER
A runtime-sized binary with no Brotli decoder inside. Only listed with --all.

0 nothing behind · 3 a decoder is behind · 1 error (nothing could be read) · 64 bad flags

7How the reading works

The fix for CVE-2026-111497 (Brotli upstream 0ed4268, backported to 1.2.1, 1.1.1 and 1.0.10) added a new decoder error, BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH (-17). Brotli compiles the names of its errors into a string table, so the fix leaves a fingerprint in every binary that links the decoder: 17 names instead of 16.

lotstamp streams each file in 8 MB windows and looks for that table. Brotli 1.1+ stores names like _ERROR_FORMAT_PADDING_1; 1.0.x stores the bare PADDING_1, so both spellings are matched. Node's zlib.constants carry the same names with a BROTLI_DECODER_ prefix; they come from the headers Node was built with, so in a binary that links a shared libbrotlidec they are ignored and the library itself is read instead. That is how /usr/bin/node on Debian gets graded by libbrotlidec.so.1, which is where the code that runs lives.

The version stamps are still read, for the report: NODE_VERSION-style strings, Bun's version, Electron's and Chromium's. They decide nothing. Bun reports Node 26.3.0 as its Node-compat level; Electron apps report a Node whose Brotli comes from Chromium. Version checks get both wrong.

8FAQ

My Cursor / VS Code / Windsurf says Node 24.19.0. lotstamp says FIXED. Who's right?

The decoder. Electron builds its Node against Chromium's copy of Brotli, and Chromium M148 rolled in the fix on 2026-03-18. Electron 42+ ships Chromium 148+, so the bundled Node's Brotli is fixed even though its Node version predates Node's own fix release. lotstamp shows the 17 names it found.

Does it run anything? Does it need root?

No and no. It stats and reads files; it never executes them or loads them as libraries. Files it can't open are listed as skipped. With sudo it can read other users' installs too.

Why not just compare node --version?

On the 8 AI coding tools we measured (latest Linux x64 builds, 2026-10-24), a version comparison flagged 6 as exposed. All 6 carry the fixed decoder. On a Debian 13 box it flagged 4 of 7 copies and missed the 2 that weren't Node at all: Python's brotli module and the system libbrotlidec Debian's node actually uses. The data is on the belt and in site/demo.json.

How fast is it?

1.4 s on the Debian box the belt shows (27 files read); it reads only runtime-sized binaries (8 MB+) and Brotli libraries, four at a time. LOTSTAMP_TRACE=1 shows where the time goes.

VS Code shows a BEHIND line for vsce-sign. Is it reachable?

The grade is real: VS Code 1.143.1 bundles @vscode/vsce-sign, the helper VS Code runs to verify extension signatures. On Linux x64 it is a .NET 9.0.9 single-file app (its embedded deps.json names runtimepack.Microsoft.NETCore.App.Runtime.linux-x64/9.0.9), and the .NET host statically links System.IO.Compression.Native, which carries Brotli's C decoder. That table has 16 names and no BLOCK_SWITCH. VS Code's own runtime reads FIXED.

Reachability, from the public bytes and the public .NET source (not a dynamic test):

  • In .NET, the managed code that calls BrotliDecoderDecompressStream lives in System.IO.Compression.Brotli.dll (BrotliStream, BrotliDecoder). The bundle's assembly list does not include that assembly; it ships System.IO.Compression.dll and System.IO.Compression.ZipFile.dll, which handle ZIP/Deflate only. That is what a VSIX and its signature archive are.
  • The only network path we found is the X.509 chain builder fetching AIA certificates, CRLs and OCSP over plain http (X509ResourceClient.cs). It builds a default SocketsHttpHandler, whose AutomaticDecompression is off, so no Content-Encoding: br response is decoded, and HttpClient's decompression path would need the missing Brotli assembly anyway.

So, as shipped in 1.143.1 on Linux x64, we found no path for untrusted Brotli data to reach that decoder. lotstamp still grades it BEHIND, because it grades code, not reachability, and the decoder only goes away when Microsoft rebuilds vsce-sign on a .NET servicing release with a fixed Brotli. This was read on Linux only; the macOS and Windows vsce-sign builds have not been inspected yet. If you know of a path we missed, open an issue.

An AppImage shows UNKNOWN.

Its payload is a compressed squashfs. Extract it (./App.AppImage --appimage-extract, which does run the AppImage's own runtime, or unsquashfs) and point lotstamp at squashfs-root/.

Can it check other CVEs?

Not yet. The probe is general (look for a string a fix added), and the advisory is a JSON file in internal/advisory. The roadmap lists what would come next.

Something was graded wrong.

Please open an issue with the --json finding; the evidence block is enough to reproduce it without the file.
