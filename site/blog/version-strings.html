Your node -v is not your Brotli decoder

Why version strings mislead for CVE-2026-111497 (Node2Shell), and how lotstamp grades the decoder by an error name the fix compiled into it. Everything below was measured on Linux x64 on 2026-10-24. macOS and Windows have not been measured on real machines yet.

1The bug lives in a library, not in a version number

CVE-2026-111497 is an out-of-bounds write in Brotli's C decoder (c/dec/decode.c), present from Brotli 1.0.3 through 1.2.0 and fixed in 1.0.10, 1.1.1 and 1.2.1 (OSV). Node fixed it in 22.23.4, 24.22.1 and 26.12.1 on 2026-10-21; Bun in 1.4.4; PyPI brotli in 1.2.1; Debian in DSA-6582-1 and DLA-4855-1.

That list invites a simple check: read the Node version, compare. The trouble is that the decoder you actually run is often not the one that version number describes. Someone reported exactly this confusion against Codex's bundled runtime in openai/codex#56076.

2Three ways the version string is wrong

Bun says Node 26.3.0

Every Bun binary we read contains the URL nodejs.org/download/release/v26.3.0/node-v26.3.0-headers.tar.gz. That is Bun's Node-compatibility level, not a Node runtime. A check that greps for the Node version calls Claude Code 2.1.310 and OpenCode 1.19.4 "Node 26.3.0, below 26.12.1, vulnerable". Both ship Bun 1.4.4, which has the fix.

Electron's Node uses Chromium's Brotli

Electron builds Node against Chromium's copy of Brotli: its build_add_gn_build_files.patch maps deps/brotli to //third_party/brotli:dec. Chromium rolled Brotli to cfa184a (2026-03-18) in M148, which already contains upstream commit 0ed4268 (2026-02-27, "Detect and report invalid stream earlier"); Brotli 1.2.1 is that commit cherry-picked. So Cursor 3.27.12 and Windsurf 1.126.0 (Electron 42, "Node 24.19.0"), VS Code 1.143.1 (Electron 43, "Node 24.21.0") and Kiro 1.4.26 (Electron 44, "Node 24.21.0") all look behind Node 24.22.1 and all carry the fixed decoder.

Debian's node uses the system library

Debian 13's /usr/bin/node (v20.19.2) is built with --shared-brotli: it goes through libnode.so.115 to libbrotlidec.so.1. The Node version says nothing either way; the package libbrotli1 decides. On our box it was 1.1.0-2+b7, pre-fix, and 1.1.0-2+deb13u1 fixes it without changing the upstream version.

Net result on the latest Linux x64 builds of 8 AI coding tools: a version-string check flags 6 of 8 as exposed; reading the decoder, 0 of 8 are. The pre-fix decoders on the same box were elsewhere: the Debian system library behind /usr/bin/node, PyPI brotli 1.2.0 in ~/.local, a stale npm-installed Claude Code 2.1.197 (Bun 1.4.0) and a pnpm-installed Bun 1.4.2.

3The fingerprint the fix left behind

Between Brotli v1.2.0 and v1.2.1 only c/dec/decode.c and decode.h change. The fix adds one decoder error, BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH (-17), in a slot that was reserved. Brotli keeps a table of error names for BrotliDecoderErrorString, so that name is compiled into every binary carrying the decoder. The 1.1.1 and 1.0.10 backports add it too.

decoderFORMAT error names
pre-fix: Node 20.19.5, 24.22.0; Bun 1.4.0, 1.4.2, 1.4.3; Debian 13 libbrotlidec 1.1.0-2+b7; PyPI brotli 1.2.016, no BLOCK_SWITCH
fixed: Node 22.23.4, 24.22.1; Bun 1.4.4; Debian 13 1.1.0-2+deb13u1; Debian 12 deb12u117, BLOCK_SWITCH present

Two details made this harder than a single grep:

  • Two spellings. Brotli 1.0.x stores bare names (FORMAT_BLOCK_SWITCH), 1.1 and later store _ERROR_FORMAT_*. A first draft graded Debian 12's fixed 1.0.9 backport as unfixed until we read the real .deb; both forms are matched now.
  • Node also carries the names as constants. zlib.constants exposes BROTLI_DECODER_ERROR_FORMAT_*, compiled from build-time headers. Debian's libnode.so.115 has only those constants and links the shared library, so a plain string scan would grade the wrong file. lotstamp reads dynamic imports (ELF, Mach-O, PE) and, when a file links libbrotlidec, grades the library and reports the file under it.

When a package database answers (dpkg today), its version wins over the marker. lotstamp never calls a copy FIXED without the marker or an authoritative package version, and it never executes what it reads.

4What this does not tell you

  • It grades code, not reachability. VS Code's vsce-sign helper carries a pre-fix decoder; the FAQ explains why we found no path for untrusted data to reach it, and it is still listed as BEHIND.
  • Packed payloads (AppImage) read UNKNOWN until extracted.
  • All numbers here are from Linux x64. Mach-O and PE parsing runs in CI on macOS and Windows runners, but app discovery there has only seen synthetic layouts.
