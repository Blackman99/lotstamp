node -v 不等于你在跑的 Brotli 解码器

为什么版本号会在 CVE-2026-111497（Node2Shell）上误导人，以及 lotstamp 怎样用修复编进二进制的一个错误名来判定解码器。下文所有数据都是 2026-10-24 在 Linux x64 上实测的；macOS 和 Windows 还没有在真机上测过。

1漏洞在库里，不在版本号里

CVE-2026-111497 是 Brotli C 解码器（c/dec/decode.c）的越界写，影响 Brotli 1.0.3 到 1.2.0，修复版本是 1.0.10、1.1.1、1.2.1（OSV）。Node 在 2026-10-21 发布 22.23.4、24.22.1、26.12.1 修复；Bun 是 1.4.4；PyPI brotli 是 1.2.1；Debian 是 DSA-6582-1 和 DLA-4855-1。

看到这张表，最自然的做法是读 Node 版本号再比较。问题在于，你实际运行的解码器经常不是那个版本号描述的那一份。有人在 openai/codex#56076 里就 Codex 自带运行时提出了同样的疑问。

2版本号出错的三种情况

Bun 自称 Node 26.3.0

我们读过的每个 Bun 二进制里都有 nodejs.org/download/release/v26.3.0/node-v26.3.0-headers.tar.gz 这个 URL。这是 Bun 的 Node 兼容级别，不是 Node 运行时。按字符串找 Node 版本的检查会把 Claude Code 2.1.310 和 OpenCode 1.19.4 判成「Node 26.3.0，低于 26.12.1，有漏洞」，而它们用的是已修复的 Bun 1.4.4。

Electron 里的 Node 用的是 Chromium 的 Brotli

Electron 编译 Node 时链接 Chromium 自带的 Brotli：build_add_gn_build_files.patch 把 deps/brotli 换成 //third_party/brotli:dec。Chromium 在 M148 把 Brotli 升到 cfa184a（2026-03-18），其中已包含上游提交 0ed4268（2026-02-27，"Detect and report invalid stream earlier"），Brotli 1.2.1 就是 cherry-pick 了这个提交。所以 Cursor 3.27.12、Windsurf 1.126.0（Electron 42，「Node 24.19.0」）、VS Code 1.143.1（Electron 43，「Node 24.21.0」）、Kiro 1.4.26（Electron 44，「Node 24.21.0」）看上去都落后于 24.22.1，实际带的都是修复后的解码器。

Debian 的 node 用系统库

Debian 13 的 /usr/bin/node（v20.19.2）用 --shared-brotli 编译，经 libnode.so.115 调用 libbrotlidec.so.1。这时 Node 版本号说明不了任何事，要看 libbrotli1 包：我们机器上是修复前的 1.1.0-2+b7；1.1.0-2+deb13u1 修复了它，上游版本号却没变。

结果：在 8 个 AI 编程工具最新的 Linux x64 版本上，按版本号判断有 6 个受影响；读解码器本身，0 个。同一台机器上真正修复前的解码器在别处：/usr/bin/node 背后的 Debian 系统库、~/.local 里的 PyPI brotli 1.2.0、一个 npm 装的旧版 Claude Code 2.1.197（Bun 1.4.0），以及 pnpm 装的 Bun 1.4.2。

3修复留下的指纹

Brotli 从 v1.2.0 到 v1.2.1 只改了 c/dec/decode.c 和 decode.h。修复新增了一个解码错误 BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH（-17），占用了原来保留的位置。Brotli 为 BrotliDecoderErrorString 维护一张错误名表，所以这个名字会被编进每个带解码器的二进制。1.1.1 和 1.0.10 的回移植也加了它。

解码器FORMAT 错误名
修复前：Node 20.19.5、24.22.0；Bun 1.4.0、1.4.2、1.4.3；Debian 13 libbrotlidec 1.1.0-2+b7；PyPI brotli 1.2.016 个，没有 BLOCK_SWITCH
修复后：Node 22.23.4、24.22.1；Bun 1.4.4；Debian 13 1.1.0-2+deb13u1；Debian 12 deb12u117 个，有 BLOCK_SWITCH

有两个细节让它不只是一次 grep：

  • 两种写法。Brotli 1.0.x 存的是裸名字（FORMAT_BLOCK_SWITCH），1.1 起是 _ERROR_FORMAT_*。初版曾把 Debian 12 已修复的 1.0.9 回移植判成未修复，读了真实的 .deb 才发现；现在两种写法都匹配。
  • Node 里还有同名常量。zlib.constants 暴露 BROTLI_DECODER_ERROR_FORMAT_*，来自编译时的头文件。Debian 的 libnode.so.115 只有这些常量、并链接共享库，单纯扫字符串会判错文件。lotstamp 读取动态导入（ELF、Mach-O、PE），文件链接了 libbrotlidec 时就判定那个库，并把文件列在它下面。

包数据库能回答时（目前是 dpkg），以包版本为准。lotstamp 没有标记或权威包版本时绝不判 FIXED，也从不执行它读取的文件。

4它不能告诉你的

  • 它判定的是代码，不是可达性。VS Code 的 vsce-sign 带着修复前的解码器；FAQ 说明了为什么我们没找到不可信数据到达它的路径，它仍被列为 BEHIND。
  • 打包压缩的载荷（AppImage）在解开前判为 UNKNOWN。
  • 本文数据全部来自 Linux x64。Mach-O 和 PE 解析在 CI 的 macOS、Windows runner 上有测试，但那边的应用发现只跑过模拟目录结构。
curl -fsSL https://blackman99.github.io/lotstamp/install.sh | sh
lotstamp            # 扫描常见位置
lotstamp dist/      # 或者一个构建产物
